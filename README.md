# Система управления грантовыми конкурсами (Лабораторная работа №4)

REST API сервис на Spring Boot с интеграцией механизмов аутентификации, авторизации и защиты данных с использованием **Spring Security**.

## Стек технологий
* **Java 25**
* **Spring Boot 4.1.1**
* **Spring Security 6+**
* **Spring Data JPA / Hibernate**
* **PostgreSQL 18**
* **Maven**

---

## Архитектура безопасности

### 1. Аутентификация и хранение паролей
* Аутентификация реализована по протоколу **HTTP Basic Auth**.
* Пароли пользователей защищены с помощью алгоритма хеширования **BCrypt** (`PasswordEncoder`). В открытом виде пароли не сохраняются и не возвращаются в API (`@JsonProperty(access = Access.WRITE_ONLY)`).
* Сущность `User` расширена полями контроля состояния учетной записи:
   * `enabled` — флаг активности аккаунта;
   * `accountNonLocked` — флаг отсутствия блокировки.
* Класс `CustomUserDetailsService` загружает пользователя из PostgreSQL и валидирует статус активности при каждом входе.

### 2. Регистрация пользователей
* Эндпоинт: `POST /api/auth/register` (доступен без аутентификации).
* Валидация входных данных DTO:
   * проверка корректности email;
   * проверка сложности пароля через регулярное выражение (не менее 8 символов, заглавная буква, строчная буква, цифра и специальный символ).
* **Защита от повышения привилегий:** при самостоятельной регистрации пользователю всегда присваивается базовая роль `ROLE_APPLICANT`. Назначение ролей администратора и эксперта доступно только администратору через CRUD-эндпоинты.

### 3. CSRF-защита
* Для защиты от атак межсайтовой подделки запросов (CSRF) для всех изменяющих состояние методов (`POST`, `PUT`, `DELETE`, `PATCH`) включена проверка CSRF-токена.
* Токен хранится в Cookie с помощью `CookieCsrfTokenRepository.withHttpOnlyFalse()` (cookie `XSRF-TOKEN`).
* Предоставлен публичный эндпоинт `GET /api/csrf` для получения токена клиентами, передаваемого в заголовке `X-XSRF-TOKEN`.

### 4. Ролевая модель и авторизация
Включен контроль доступа на уровне маршрутов в `SecurityFilterChain` и на уровне методов через `@EnableMethodSecurity` и `@PreAuthorize`:

| Роль | Разрешенные операции |
| :--- | :--- |
| **`ROLE_ADMIN`** | Создание/удаление конкурсов, финализация конкурса (`finalize`), выплата грантов (`disburse`), управление пользователями (`/api/users/**`). |
| **`ROLE_APPLICANT`** | Подача заявок на конкурс (`submit`), отзыв собственных заявок (`withdraw`). |
| **`ROLE_EXPERT`** | Экспертная оценка заявок со шкалой 0–100 (`evaluate`). |
| **Любой авторизованный** | Просмотр списка открытых конкурсов (`GET /api/grant-competitions/**`). |

### 5. Обработка ошибок безопасности (без утечки данных)
* **`RestAuthenticationEntryPoint` (401 Unauthorized):** перехватывает запросы неаутентифицированных пользователей и возвращает чистый JSON `{"error": "Unauthorized", ...}`.
* **`RestAccessDeniedHandler` (403 Forbidden):** перехватывает попытки выполнения операций при нехватке полномочий (например, соискатель пытается создать конкурс) и возвращает `{"error": "Forbidden", ...}`.
* **`GlobalExceptionHandler` (400 Bad Request):** обрабатывает ошибки валидации формата/пароля и исключения бизнес-логики (`BusinessLogicError`).

## Тестирование и демонстрация

Полный сценарий успешных и отказных операций описан в файле **`requests.http`**:
1. Получение CSRF-токена (`GET /api/csrf`).
2. Ошибка 400 при регистрации со слабым паролем.
3. Успешная регистрация соискателя со сложным паролем.
4. Ошибка 401 Unauthorized (обращение без Basic Auth).
5. Ошибка 403 Forbidden (попытка выполнения административного действия соискателем).
6. Сквозной бизнес-процесс: конкурс (`ADMIN`) $\rightarrow$ заявка (`APPLICANT`) $\rightarrow$ оценка (`EXPERT`) $\rightarrow$ подведение итогов (`ADMIN`) $\rightarrow$ выплата (`ADMIN`).
